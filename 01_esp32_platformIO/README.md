## ESP32 FreeRTOS vs 아두이노 블로킹 제어 시스템 성능 평가 결과  
동일한 하드웨어(ESP32 Dev Module) 환경에서 단일 스레드 기반 제어 방식(Arduino Blocking)과   
실시간 운영체제 기반 멀티태스킹 제어 방식(FreeRTOS Polling, FreeRTOS Interrupt)의 
실시간성, 결정성, 그리고 시스템 자원 효율성을 정량적으로 대조 평가하였습니다.  
---

## [소스코드 파일 구성]
본 성능 평가 및 리포트 작성에 사용된 세 가지 소스코드 파일은 `src/` 폴더 내에 백업되어 있으며, 각 아키텍처별로 다음과 같은 특징을 가집니다. 테스트 시 원하는 파일의 코드를 `main.cpp`로 붙여넣기하여 빌드 및 업로드할 수 있습니다.

1. **`arduino_blocking.cpp.bak` (단일 스레드 블로킹 버전)**
   - **특징**: 전통적인 아두이노의 `setup()` 및 `loop()` 단일 스레드 구조입니다. 온습도 센서 수집 주기 제어를 위해 `delay(2000)`와 `delay(200)` 등 하드웨어 블로킹 함수를 사용합니다.
   - **목적**: 다른 센서의 블로킹 대기 시간이 안전 제어장치의 반응 지연(Latency)에 주는 영향과 입력 누락(비결정성) 문제를 증명하기 위한 비교 대조군입니다.

2. **`rtos_flame_test_version.cpp.bak` (RTOS 태스크 폴링 버전)**
   - **특징**: FreeRTOS 스케줄러를 도입하여 센서 수집 및 제어 기능을 독립된 멀티태스크(`button_task`, `flame_task_test`, `dht_task`)로 나누어 실행합니다. 물리 버튼 입력을 20ms 주기로 `digitalRead()`를 통해 지속적으로 확인(Polling)합니다.
   - **목적**: 멀티태스킹 도입을 통해 2초의 온습도 수집 대기 시간 동안에도 제어 흐름이 중단되지 않고 실시간성을 유지(결정성 확보)할 수 있음을 보여주는 모델입니다.

3. **`rtos_interrupt_version.cpp.bak` (RTOS 인터럽트 연동 버전 - 최종 코드)**
   - **특징**: 물리 버튼 감지를 하드웨어 외부 인터럽트(`button_isr`)로 처리하고, 이벤트 발생 시 획득한 고정밀 시간 스탬프와 시리얼 UI 명령어를 통합 명령어 태스크(`command_task`)에서 플래그 감시 방식으로 20ms마다 처리합니다. 
   - **목적**: 불필요한 레지스터 폴링(digitalRead) 연산을 완전히 차단하여 응답 속도를 극대화하고 CPU 부하와 전력 소모를 최소화한 최종 최적화 제어 모델입니다.

## 0. 실험 조건 및 환경 설정 (Experimental Setup)
실험의 공정성 및 타당성을 확보하기 위해 세 가지 버전 모두 아래와 같이 동일한 핀 맵과 센서/동작 주기 조건으로 구성하여 테스트를 수행하였다.

### 1) 대상 하드웨어 및 시스템 사양
- **MCU**: ESP32 Dev Module (Xtensa Dual-Core 240MHz, 320KB RAM, 4MB Flash)
- **주요 핀 맵**:
  - `BUTTON_PIN` (비상 정지 버튼): GPIO 0 (내부 풀업 저항 적용)
  - `LED_PIN` (긴급 정지 LED 표시): GPIO 2
  - `DHT_PIN` (DHT11 온습도 센서): GPIO 4
  - `FLAME_TEST_PIN` (실험을 위해 화재 감지를 버튼으로 대체): GPIO 32 (내부 풀업 저항 적용)

### 2) 센서/동작 주기 설정 (동일 대조 조건)
- **온습도 수집 주기**: **2,000 ms** (아두이노 `delay(2000)` 및 RTOS `dht_task` 내 `vTaskDelay(2000)`로 동일)
- **화재 감지 감시 주기**: **200 ms** (아두이노 `delay(200)` 및 RTOS `flame_task_test` 내 `vTaskDelay(200)`로 동일)
- **물리 버튼 감시 주기 (RTOS)**: **20 ms** (RTOS Polling의 `button_task` 및 RTOS Interrupt의 `command_task` 내 `vTaskDelay(20)`로 동일)
- **물리 버튼 감시 주기 (아두이노)**: 별도 주기 없음 (시스템 루프 주기에 종속적 - 일반 상태: **2,000 ms**, 화염 상태: **200 ms**)

### 3) 성능 측정 시나리오
- **일반 상태 (Normal State)**: DHT11 온습도 모니터링 루프가 2,000ms 주기로 작동 중일 때, **긴급 정지(E-Stop) 물리 버튼 입력 감지 지연 시간 측정 (10회 반복)**
- **화염 상태 (Flame State)**: 화염 발생으로 온습도 루프가 차단되고 200ms 주기의 화염 루프가 작동 중일 때, 긴급 정지 물리 버튼 입력 감지 지연 시간 측정 (5회 반복)
- **성능 측정 도구**: ESP32 보드 내부의 하드웨어 마이크로초 타이머(`micros()`)를 활용하여 **버튼 누름 검출 시점(인터럽트 시점)과 실제 LED가 켜진 시점의 시간 차를 연산하여 PC 시리얼 통신을 통해 실시간 수집 및 로깅**

### 2) 핵심 지표 분석
#### 지표 A: 딜레이 시간의 비결정성 전이
* **아두이노 블로킹 버전**의 결과를 보면 시스템 상태에 따라 응답 시간이 크게 변동합니다.
  * **일반 상태** (온습도 루프 작동 중): 평균 지연 **1,295ms**, 최대 지연 **1,876ms** (약 2초에 달함).
  * **화염 상태** (온습도 루프가 꺼지고 화염 루프만 작동 중): 평균 지연 **135ms**, 최대 지연 **189ms** (약 0.2초).
* **의의**: 아두이노 방식에서는 **안전장치(정지 버튼)의 반응 속도가 다른 센서의 딜레이(DHT11 2초 딜레이 vs 화염 0.2초 딜레이)에 볼모로 잡혀 있음**을 뜻합니다. 만약 다른 엔지니어가 코드에 5초짜리 통신 딜레이를 추가한다면, 긴급 정지도 5초 뒤에 동작하게 되는 치명적인 안전 위험(Safety Hazard)을 가집니다.

#### 지표 B: 태스크 격리 및 시간 결정성 (FreeRTOS가 유리)
* **RTOS 두 버전(인터럽트/폴링)**은 일반 상태와 화염 상태에 관계없이 응답 속도가 **항상 20ms 이내**로 완벽하게 묶여 있습니다.
  * 일반 상태 평균: 10~14ms
  * 화염 상태 평균: 9~12ms
* **의의**: 온습도 센서가 2초 동안 멈추든(Blocked), 화염 센서 태스크가 200ms 주기로 돌든 상관없이 **긴급 정지 태스크는 독립된 시간 영역(Time Domain)을 보장받는다**는 의미입니다. 이를 통해 시스템 부하에 상관없이 일정한 응답 속도를 제공하는 **실시간 결정성(Real-time Determinism)**을 실현했습니다.

#### 지표 C: 인터럽트(ISR)와 폴링(Polling)의 미세 성능 차이
* **인터럽트+Task** 버전이 **폴링** 버전보다 **평균 지연 속도가 약 3~4ms 더 빠릅니다.** (10.42ms vs 14.35ms)
* **이유**:
  * **폴링 방식**: 태스크 주기(20ms)와 물리적 버튼 입력 순간이 맞지 않으면 다음 주기까지 기다린 후 GPIO 레지스터를 직접 읽어야(digitalRead) 합니다.
  * **인터럽트 방식**: 버튼이 눌리는 그 마이크로초 단위의 즉시 인터럽트가 실행되어 메모리에 플래그(`button_pressed = true`)를 꽂아둡니다. `command_task`는 매 주기마다 무거운 GPIO 조회(digitalRead)를 할 필요 없이 가볍게 메모리 플래그 변수만 확인하므로 응답 속도가 훨씬 빠르고 편차가 좁아집니다.
* **의의**: 인터럽트 방식이 반응 속도 면에서 더 뛰어날 뿐만 아니라, 불필요한 레지스터 폴링 연산을 피하므로 **CPU 전력 효율성 및 가용 시간 최적화** 측면에서 가장 우수한 아키텍처임을 보여줍니다.

## 2. 메모리 성능 비교

### 1) Static Memory
1. **RTOS 인터럽트+Task**
   - RAM:   [=         ]   6.7% (used **21976** bytes from 327680 bytes)
   - Flash: [==        ]  20.9% (used **274373** bytes from 1310720 bytes)
2. **RTOS 폴링**
   - RAM:   [=         ]   6.7% (used **21976** bytes from 327680 bytes)
   - Flash: [==        ]  20.9% (used **274565** bytes from 1310720 bytes)
3. **아두이노 블로킹**
   - RAM:   [=         ]   6.7% (used **21984** bytes from 327680 bytes)
   - Flash: [==        ]  20.9% (used **273969** bytes from 1310720 bytes)

* **결과 분석**:
  1) **RAM (SRAM 전역변수 영역)**:
     - **아두이노 블로킹(21,984 Byte) > RTOS(21,976 Byte)**
     - RTOS 버전들은 변수의 스택(지역 변수) 활용 등을 통해 전역변수 개수가 줄어들어 미세하게 static RAM 용량이 감소했습니다.
  2) **Flash (프로그램 저장 영역)**:
     - **RTOS 폴링(274,565 Byte) > RTOS 인터럽트(274,373 Byte) > 아두이노 블로킹(273,969 Byte)**
     - 아두이노 버전이 가장 작습니다 (RTOS 커널 라이브러리 및 태스크 관리 함수 유무에 따른 영향).
     - RTOS 폴링 버전이 인터럽트 버전보다 **192바이트** 더 큽니다. 이는 폴링 버전이 태스크의 동적 생성 및 삭제 관련 제어 코드가 더 많이 포함되어 컴파일되었기 때문입니다.

### 2) Dynamic Memory (Heap)
1. **RTOS 인터럽트+Task**
   - normal : Stack Margin: **220** bytes | System Free Heap: **342668** bytes
   - emergency : Stack Margin: **192** bytes | System Free Heap: **342404** bytes
2. **RTOS 폴링**
   - normal : Stack Margin: **228** bytes | System Free Heap: **342660** bytes
   - emergency : Stack Margin: **204** bytes | System Free Heap: **342396** bytes
3. **아두이노 블로킹**
   - normal : Stack Margin: **6300** bytes | System Free Heap: **349960** bytes
   - emergency : Stack Margin: **6300** bytes | System Free Heap: **349960** bytes

* **결과 분석**:
  1) **System Free Heap (시스템 자유 힙)**
     - 아두이노 버전과 RTOS 버전 간에 정확하게 약 **7.3 KB**의 동적 힙 메모리 소모 차이가 발생합니다.
     - RTOS 버전에서는 `xTaskCreate`를 통해 `Flame Task` (2048B), `DHT Task` (2048B), `Button(또는 Command) Task` (2048B) 총 3개의 태스크를 런타임 힙 영역에 동적으로 할당하였기 때문입니다.
     - RTOS에서 비상(emergency) 정지 시점에 미세하게 힙 감소가 발생한 이유: 비상 상황 직후 힙이 즉시 반환(Idle Task에 의해 해제)되지 않은 상태에서 새로운 복구 태스크(`recover_task`)를 생성했기 때문입니다.
  2) **Stack Margin (태스크 스택 여유 공간)**
     - RTOS 버전에서는 사용자가 직접 2,048바이트로 태스크 스택을 제한하여 생성하였습니다.
     - 이 중 DHT Task의 여유 공간이 220바이트 내외라는 것은 실제 실행 중에 스택을 약 **1,820바이트 이상 타이트하게 사용 중**이라는 의미입니다. (DHT 라이브러리는 하드웨어 시간 측정 및 실수형(Float) 연산으로 인해 스택 소모량이 많음)
     - 따라서 추후 시스템 안정성을 위해 DHT Task의 할당 스택 크기를 기존 2,048바이트에서 **3,072바이트**로 확장 튜닝하는 것이 권장됩니다.

## 3. CPU 사용량 및 성능 비교

1. **폴링 방식 (RTOS Polling / Arduino)**
   - **동작**: 매 주기(20ms)마다 `digitalRead(BUTTON_PIN)` 함수를 호출합니다.
   - **효율**: 이 함수는 하드웨어 레지스터 주소 참조, 비트 연산, 조건문 판단 등 수십 개의 CPU 클럭 사이클을 매초 수백 번 반복 소모하므로 상대적으로 전력 소모와 연산 부하가 큽니다.
2. **인터럽트 방식 (RTOS Interrupt)**
   - **동작**: 평소에는 CPU가 버튼 하드웨어를 감시하지 않고, 단순 RAM 내부 변수 `button_pressed` (Boolean, 1바이트) 값만 검사합니다.
   - **효율**: 1사이클 근처의 극히 가벼운 비교 연산만 수행하므로 CPU 연산 비용이 물리적으로 거의 발생하지 않으며, 전력 소모를 크게 줄일 수 있습니다.
3. **아두이노 `delay()`**:
   - 루프를 돌며 비지웨이팅(Busy-waiting)을 하거나 백그라운드 태스크에 대기 권한을 양보하지만, 메인 스레드 실행 흐름 자체를 제어권을 넘기지 않고 **특정 시간 동안 완전히 묶어두어 시스템을 블로킹(Blocking)**합니다.
4. **FreeRTOS `vTaskDelay()`**:
   - 호출 즉시 해당 태스크는 `Blocked` 상태로 들어가 스레드 대기 큐로 이동하며, CPU 제어권을 즉각 운영체제(커널)의 `Idle Task`로 반환합니다. 이 대기 상태 동안 CPU는 깊은 절전 상태(Light Sleep)로 들어가거나 다른 우선순위 태스크 연산에 100% 집중할 수 있게 됩니다.

## 4. 최종 결론

### 1) 응답시간 성능 고찰
* **아두이노 (동작의 비결정성)**  
  다른 태스크의 블로킹 함수(`delay()`) 길이에 따라 안전 버튼의 지연 시간이 비례하여 증가하므로 실시간성이 요구되는 방재 시스템에 치명적입니다. 또한, 폴링 방식으로 구현 시 delay 시간 동안 버튼 클릭 자체가 누락되는 현상이 발생하여 신뢰성에 큰 위협이 됩니다.
* **RTOS 폴링 (결정성 확보)**  
  멀티태스킹 스케줄링을 통해 온습도 딜레이와 무관한 균일한 반응성(20ms 내외)을 확보하였습니다. 다만 매 주기 레지스터를 조회하므로 자원 소모가 발생합니다. (인간의 버튼 누름은 100~300ms 동안 유지되므로 20ms 주기 폴링 시 누락은 없으나, 지터/레이턴시가 주기 시간만큼 존재함)
* **RTOS 인터럽트 (실시간성 및 효율성 극대화)**  
  하드웨어 인터럽트로 이벤트 시점을 즉각 기록하고 플래그 기반으로 감시하여 가장 빠른 응답 속도와 자원 효율을 극대화한 최고의 아키텍처입니다. (하드웨어가 엣지를 즉시 검출하여 **1마이크로초 미만의 매우 짧은 입력도 100% 포착 가능**)

#### [전체 응답시간 비교 요약 (일반 상태 기준)]
- **아두이노 블로킹**: **평균 1,295.01 ms** (최대 1,876.41 ms 지연)
- **RTOS 폴링**: **평균 14.35 ms** (아두이노 대비 응답 시간 **98.89%** 감소, 약 **90.2배** 빨라짐)
- **RTOS 인터럽트**: **평균 10.42 ms** (아두이노 대비 응답 시간 **99.20%** 감소, 약 **124.3배** 빨라짐)

### 2) 자원 소모량 결과 고찰
- **메모리(Flash/SRAM)**:
  - FreeRTOS를 적용한 버전들은 커널 및 태스크 할당으로 인해 기본 아두이노 버전 대비 **정적 메모리(Flash) 소모량이 약 0.15% 미만**으로 아주 작게 증가하였습니다.
  - 런타임 가용 힙 메모리는 약 **7,300 Byte 감소(감소율 전체 가용 메모리의 약 2.08% ~ 2.09% 수준)**에 불과합니다.
- **CPU 및 전력 효율**: 메모리 소모는 매우 소폭 증가했으나, `vTaskDelay`를 통한 적극적인 CPU 양보 모델과 인터럽트를 통한 레지스터 접근 최소화 설계는 MCU의 활성 연산 시간을 감소시켜, 최종적으로 시스템 수명 연장과 발열 감소 등 하드웨어 자원 효율성에서 훨씬 우수한 결과를 도출합니다.
