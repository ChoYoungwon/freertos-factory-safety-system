# ESP32 FreeRTOS vs 아두이노 블로킹 세이프티 제어 시스템 성능 평가 결과

본 평가 보고서는 동일한 하드웨어(ESP32 Dev Module) 환경에서 단일 스레드 기반 제어 방식(Arduino Blocking)과 실시간 운영체제 기반 멀티태스킹 제어 방식(FreeRTOS Polling, FreeRTOS Interrupt+Preemption)의 실시간성, 결정성, 그리고 시스템 자원 효율성을 정량적으로 대조 평가한다.

---

## 1. 실험용 소스코드 파일 구성

본 성능 평가에 사용된 세 가지 소스코드 파일은 `src/` 폴더 내에 백업되어 있으며, 각 아키텍처별로 다음과 같은 특징을 가집니다. 테스트 시 원하는 파일의 코드를 `main.cpp`에 붙여넣어 빌드 및 업로드할 수 있습니다.

1. **`arduino_blocking.cpp.bak` (단일 스레드 블로킹 버전)**
   - **특징**: 전통적인 아두이노의 `setup()` 및 `loop()` 단일 스레드 구조입니다. 온습도 센서 수집 주기(2초) 제어를 위해 `delay(2000)` 등 하드웨어 블로킹 함수를 사용합니다.
   - **동작**: 비상 정지 인터럽트 발생 시 플래그를 세우지만, 2초 딜레이 루프가 끝날 때까지 온습도 측정 블록을 빠져나오지 못해 설비 정지 분기 진입이 지연됩니다.

2. **`rtos_polling.cpp.bak` (RTOS 태스크 폴링 버전)**
   - **특징**: FreeRTOS 스케줄러를 도입하여 센서 수집 및 제어 기능을 독립된 멀티태스크(`button_task`, `flame_task_test`, `dht_task`)로 나누어 실행합니다. 물리 버튼 입력을 20ms 주기로 `digitalRead()`를 통해 지속적으로 확인(Polling)합니다.
   - **동작**: 버튼 입력을 감지하면 즉시 온습도 태스크와 화재 감지 태스크를 강제 사살(`vTaskDelete`)하고 복구 대기 태스크(`recover_task`)를 생성한 뒤 자신을 종료합니다.

3. **`rtos_interrupt.cpp.bak` (RTOS 인터럽트+선점 연동 버전 - 최종 최적화 코드)**
   - **특징**: 물리 버튼 감지를 하드웨어 외부 인터럽트(`button_isr`)로 포착하고, Task Notification(`vTaskNotifyGiveFromISR`)과 `portYIELD_FROM_ISR()`을 통해 최우선순위(우선순위 10) `emergency_task`를 즉각 선점(Preemption) 실행합니다.
   - **동작**: 20ms 대기 없이 수십 마이크로초 이내에 선점된 `emergency_task`가 임계구역(`portENTER_CRITICAL`)에서 하드웨어 핀 차단을 원자적으로 실행하고, 실행 중이던 모든 센서 태스크를 즉각 중지(`vTaskDelete`)합니다.

## 2. 실험 조건 및 환경 설정

실험의 공정성과 대조군 비교의 타당성을 확보하기 위해 세 가지 버전 모두 아래와 같이 동일한 핀 맵과 동작 주기 조건으로 구성하여 테스트를 수행하였습니다.

### 1) 대상 하드웨어 및 시스템 사양
- **MCU**: ESP32 Dev Module (Xtensa Dual-Core 240MHz, 320KB RAM, 4MB Flash)
- **주요 핀 맵**:
  - `BUTTON_PIN` (비상 정지 버튼): GPIO 0 (내부 풀업 저항 적용)
  - `LED_PIN` (긴급 정지 LED 표시): GPIO 2
  - `DHT_PIN` (DHT11 온습도 센서): GPIO 4
  - `FLAME_TEST_PIN` (화재 감지 버튼): GPIO 32

### 2) 센서/동작 주기 설정 (동일 대조 조건)
- **온습도 수집 주기**: **2,000 ms** (아두이노 `delay(2000)` 및 RTOS `dht_task` 내 `vTaskDelay(2000)`로 동일)
- **화재 감지 감시 주기**: **200 ms** (아두이노 `delay(200)` 및 RTOS `flame_task_test` 내 `vTaskDelay(200)`로 동일)
- **물리 버튼 감시 주기 (RTOS Polling)**: **20 ms** (`button_task` 내 `vTaskDelay(20)`)
- **물리 버튼 감시 주기 (RTOS Interrupt+Preemption)**: **0 ms (즉각 선점)** (ISR 기반 문맥 교환으로 폴링 완전 제거)
- **물리 버튼 감시 주기 (아두이노)**: 별도 주기 없음 (시스템 루프 주기에 종속적 - 일반 상태: **2,000 ms**)

### 3) 성능 측정 시나리오
- **정지 지연 시간(Latency) 정의**: 비상 정지 물리 버튼이 눌린 순간($T_{\text{start}}$)부터, **실행 중이던 모든 일반 태스크(DHT11, 화재 감시)가 완전히 소멸(Kill/중단)되어 안전 복구 모드에 도달한 시점($T_{\text{end}}$)**까지의 시간 차 측정
- **반복 횟수**: 각 펌웨어별 긴급 정지 버튼 10회 반복 측정
- **측정 도구**: ESP32 하드웨어 마이크로초 타이머(`micros()`)를 통해 정밀 측정 후 C# WinForms UI 및 `latency_results.txt`로 실시간 수집

## 3. 응답시간(정지 지연 시간) 성능 비교 분석

### 1) 측정 데이터 통계 분석 요약 (10회 반복 측정)

| 제어 방식 | 최소 응답 시간 | 최대 응답 시간 | 평균 응답 시간 | 지터 (표준편차) |
| :--- | :---: | :---: | :---: | :---: |
| **① 아두이노 블로킹** <br> (단일 스레드 + delay) | 761.70 ms | 1,681.63 ms | **1,391.89 ms** | **324.83 ms** |
| **② RTOS 폴링** <br> (20ms 주기 핀 폴링) | 0.65 ms | 19.90 ms | **8.99 ms** | **6.99 ms** |
| **③ RTOS 인터럽트+선점** <br> (ISR 선점 + 즉각 태스크 삭제) | 0.11 ms | 0.18 ms | **0.12 ms** (122 $\mu\text{s}$) | **0.02 ms** (20 $\mu\text{s}$) |

---

### 2) 핵심 지표 분석

#### 지표 A: 아두이노 블로킹의 시간적 비결정성 (Temporal Non-determinism)
* **아두이노 버전**은 버튼이 눌린 시점에 2초 딜레이(`delay(2000)`)의 어느 지점을 지나고 있느냐에 따라 정지 지연 시간이 **761.70 ms에서 1,681.63 ms까지 극심하게 출렁입니다 (평균 1,391.89 ms, 편차 324.83 ms).**
* **의의**: 안전 제어 장치가 다른 센서의 블로킹 딜레이 시간에 완전히 종속되어 있어, 긴급 상황 발생 시 1초 이상 설비 가동이 중단되지 못하는 치명적인 안전 위험(Safety Hazard)을 가집니다.

#### 지표 B: RTOS 멀티태스킹 폴링의 실시간 결정성 확보
* **RTOS 폴링 버전**은 DHT11 태스크가 2초 동안 대기(`vTaskDelay(2000)`) 중이더라도 `button_task`가 독립적으로 20ms마다 깨어나 감시하므로, 응답 시간이 **폴링 주기인 20ms 이내(최대 19.90 ms, 평균 8.99 ms)**로 안정적으로 수렴합니다.
* **의의**: 온습도 센서 루프와 안전 제어 루프가 완벽히 격리(Isolation)되어, 센서 딜레이와 무관하게 일정한 반응성을 보장하는 실시간 결정성(Real-time Determinism)을 획득했습니다.

#### 지표 C: 인터럽트 + 즉각 선점(Preemption)을 통한 극한의 반응성
* **RTOS 인터럽트+선점 버전**은 20ms의 폴링 주기 대기를 제거하였습니다.
* 버튼이 눌리는 순간 ISR이 `emergency_task`(최고 우선순위 10)를 즉각 깨우고 `portYIELD_FROM_ISR()`로 문맥을 교환하므로, **순수 OS 문맥 교환 및 태스크 소멸 시간인 평균 0.12 ms (122 마이크로초)** 만에 설비 차단과 타 태스크 종료를 완료합니다.
* **지터(표준편차)가 0.02 ms (20 마이크로초)** 에 불과하여, 편차 없는 실시간 제어 성능을 증명합니다.

#### [전체 응답시간 비교 요약]
- **아두이노 블로킹**: **평균 1,391.89 ms** (최대 1,681.63 ms)
- **RTOS 폴링**: **평균 8.99 ms** (아두이노 대비 **99.35% 단축**, 약 **154.8배** 향상)
- **RTOS 인터럽트+선점**: **평균 0.12 ms** (아두이노 대비 **99.99% 단축**, 약 **11,409배** 향상 / 폴링 대비 **98.64% 추가 단축**, 약 **73.7배** 향상)

## 4. 메모리 및 자원 성능 비교

### 1) Static Memory (정적 메모리 사용량)

| 제어 방식 | RAM (SRAM) 사용량 | Flash (프로그램 저장) 사용량 |
| :--- | :---: | :---: |
| **① 아두이노 블로킹** | 21,984 bytes (6.7%) | 275,309 bytes (21.0%) |
| **② RTOS 폴링** | 21,992 bytes (6.7%) | 276,057 bytes (21.1%) |
| **③ RTOS 인터럽트+선점** | 21,992 bytes (6.7%) | 276,009 bytes (21.1%) |

* **Flash (바이너리 용량)**:
  - 아두이노(275,309 Byte) 대비 RTOS 버전들(약 276,000 Byte)은 FreeRTOS 커널 및 태스크 관리 함수 탑재로 인해 약 **700~748 Byte (+0.25% ~ +0.27%)** 소폭 증가하였습니다. 
  - 1% 미만의 극히 미미한 용량 증가로 1만 배 이상의 반응 속도 향상을 얻었습니다.
* **RAM (전역 변수 영역)**:
  - 아두이노 버전 대비 RTOS 버전들이 전역 태스크 핸들(`TaskHandle_t`) 추가 등으로 인해 단 **8 Byte** 증가(21,984B $\rightarrow$ 21,992B)하여 실질적인 정적 램 차이는 거의 없습니다.

### 2) Dynamic Memory (동적 메모리 및 태스크 스택 - 정지 시점 기준)

| 제어 방식 | System Free Heap (가용 힙) | 비상 정지 태스크 Stack Margin |
| :--- | :---: | :---: |
| **① 아두이노 블로킹** | 349,960 bytes | 6,300 bytes (기본 loopTask) |
| **② RTOS 폴링** | 345,076 bytes | 204 bytes (Button Task) |
| **③ RTOS 인터럽트+선점** | 342,352 bytes | 244 bytes (Emergency Task) |

* **System Free Heap (동적 힙 메모리 회수 고찰)**:
  - 아두이노 버전은 별도 태스크를 생성하지 않아 가용 힙이 가장 많습니다 (349,960 Byte).
  - **RTOS 폴링**: 정지 시점에 `button_task`가 `dht_task`와 `flame_task`를 즉시 중단하고 자신도 종료하여 `recover_task`만 남기므로, 사용하던 태스크 스택 메모리가 즉시 힙으로 반환되어 **345,076 Byte**로 가용 힙이 크게 회복됩니다.
  - **RTOS 인터럽트+선점**: `dht_task`와 `flame_task`를 중단하지만 `emergency_task`와 시리얼 통신용 `command_task`가 활성 상태로 유지되므로 힙 메모리는 **342,352 Byte**를 나타냅니다.
* **Stack Margin (스택 여유 공간)**:
  - RTOS 버전들에서 2,048 Byte로 할당된 태스크 스택 중 최저 여유 공간이 **204~244 Byte**로 측정되었습니다.
  - 이는 실행 중 스택의 약 1,800 Byte 이상을 사용하고 있음을 의미합니다.

## 5. CPU 사용량 및 제어 연산 효율성 비교

1. **폴링 방식 (RTOS Polling / Arduino)**
   - **동작**: 매 주기(20ms)마다 `digitalRead(BUTTON_PIN)` 함수를 호출하여 느린 APB 주변장치 버스를 경유해 GPIO 하드웨어 레지스터를 반복 조회합니다.
   - **효율**: 주기적인 함수 호출 및 레지스터 비트 연산으로 인해 CPU 클럭 사이클과 전력이 지속적으로 소모됩니다.
2. **인터럽트 + 즉각 선점 방식 (RTOS Interrupt+Preemption)**
   - **동작**: 평소에는 `emergency_task`가 `ulTaskNotifyTake(pdTRUE, portMAX_DELAY)` 상태로 Block되어 **CPU 점유율 0%**로 대기합니다.
   - **효율**: 핀 상태 감시는 **GPIO 하드웨어 에지 검출 회로(Flip-Flop)** 가 100% 전담하며, 이벤트 발생 시에만 마이크로초 단위로 CPU를 깨우고 임계구역(`portENTER_CRITICAL`)에서 원자적으로 처리하므로 **CPU 전력 효율성이 극대화**됩니다.
3. **아두이노 `delay()` vs FreeRTOS `vTaskDelay()`**
   - 아두이노는 단일 스레드 구조로 인해 `delay(2000)` 대기 동안 시스템 전체의 실행 흐름이 묶여버리는 블로킹(Blocking)이 발생합니다.
   - 반면 FreeRTOS의 `vTaskDelay()`는 즉시 CPU 제어권을 커널의 `Idle Task`로 양보(Yield)하여 다른 태스크를 실행하거나 저전력 절전 모드로 진입할 수 있도록 보장합니다.

## 6. 최종 종합 결론

* **아두이노 블로킹**: 다른 센서의 블로킹 딜레이(2초)에 안전장치가 종속되어 **약 1.4초의 정지 지연**과 높은 비결정성(지터 324.83 ms)을 보여 실시간 방재 시스템에 부적절합니다.
* **RTOS 폴링**: 멀티태스킹 격리를 통해 온습도 딜레이와 무관하게 **20ms 이내(평균 8.99 ms)로 설비 및 타 태스크를 정지**시키는 결정성을 확보함 (아두이노 대비 99.35% 응답 개선).
* **RTOS 인터럽트+선점**: 하드웨어 인터럽트와 Task Notification 선점 기법, 그리고 임계구역을 조합하여 폴링 대기마저 소거함으로써 **단 0.12 ms (122 마이크로초) 만에 완벽한 안전 정지**를 구현함 (아두이노 대비 99.99% 단축, 11,409배 반응 속도 향상).
* **자원 소모량**: Flash 용량 증가는 단 **+0.25%**, RAM 증가는 단 **8 Byte**에 불과하여, **극소의 자원 오버헤드로 극한의 실시간 안전 신뢰성을 구현**할 수 있음을 실험적으로 입증하였습니다..
